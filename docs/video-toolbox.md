盘点日期：2026-11-04（北京时间）。本清单记录候选工具，不代表已经安装。

## 先分清几个名字

“插件”可以作为日常统称，但实际安装和管理方式不同：

| 名称 | 可以怎样理解 | 通常放在哪里 |
| --- | --- | --- |
| 框架、代码库、依赖包 | 制作视频或实现某类效果的程序 | 用到它的项目里，版本记录在 package.json 和锁文件 |
| Skill（技能） | 给 AI 的工作方法、示例及辅助脚本，通常有 SKILL.md | 对应 AI 工具支持的技能目录或插件配置；安装位置需按官方说明确认 |
| MCP 服务 | AI 连接外部功能的接口，有的要单独运行程序 | AI 工具的连接配置及服务运行环境 |
| 独立软件 | 编辑器、语音输入、远程控制等应用 | Windows 等实际运行它的电脑上 |
| GitHub 仓库 | 一套项目文件及版本历史 | GitHub 远端；下载或克隆后才在相应电脑/工作区产生副本 |

收藏（Star）不会把软件装进项目；Fork 会增加一个你名下的仓库副本；下载 ZIP 或克隆会产生本地文件；安装依赖则会改变实际运行环境。它们不是同一个操作。

## 推荐试用顺序

先补齐长期方向和新片创意简报，再选择最小测试任务。若下片仍以代码动画为主，优先对比HyperFrames与Remotion，并按需要验证Superpowers的一项素材/审片能力。若题材是机械结构或空间镜头，则把相应专项工具提到前面。封面设计可以单独测试，不和全片渲染引擎绑定。记忆工具、遥控和输入工具按工作方式需要选用，不作为画风升级的前置安装。

## 推荐的项目组织方式

每部独立视频通常使用一个项目仓库。同一系列若大量共享素材和组件，可以使用一个系列仓库。

```text
GitHub账号
├── water-video                 已完成的《一滴水》工程
├── video-下一个主题             以后正式立项时再创建
└── video-tool-lab              以后实际试工具时再创建
    ├── hyperframes-test
    └── pixel-effects-test
```

以上后两个仓库及测试目录只是建议，目前没有创建。一个实验仓库里的不同测试应保留各自依赖和说明，避免全部装进同一个 package.json。

每个正式项目建议保持：

```text
README.md                       项目入口、当前版本、如何下载观看
docs/                           分镜、风格、工具清单、阶段状态
src/                            视频源码
public/                         真正被工程使用的素材
scripts/                        项目确实需要的辅助脚本
out/                            渲染输出，默认不新增进Git
```

GitHub 的收藏/Lists 或一份清单适合保存候选工具链接。尚未使用的工具不必下载、Fork 或安装。

## 日常管理规则

1. 先选视频效果，再选实现工具。例如机械拆解与像素爆炸需要的工具不同。
2. 候选只记名称、原始链接、用途和状态：候选 → 已核验 → 测试中 → 采用/停用。
3. 试用先做5–10秒，记录实际效果、安装位置、版本、所需硬件和费用；达标后才给正式项目增加依赖。
4. 实际采用的依赖保留锁文件；技能和MCP还需记录适配的AI工具与所需服务，不能只写“装了”。密钥放安全配置，不写进Git。
5. 新项目结束时更新README、当前组合名称、交付文件名和已验证的运行方法。正式成片发布仍由用户决定。
6. 清理时先列出文件、大小、用途和备份位置，再处理。历史素材、大文件和旧分支不自动删除；Git历史瘦身需要独立计划，不把普通整理变成强推历史。

## 只读自动盘点

在项目根目录执行：

```bash
node scripts/project-inventory.mjs
```

它只读取当前工程和本地Git信息，列出当前分支、直接依赖、未提交状态、已跟踪媒体及大文件。它不会查询所有远端仓库、安装插件、移动文件或删除历史。换到新工程也可以复用该脚本。

以后可直接给AI这样的工作要求：

> 按工具清单管理新项目。先盘点已有能力，根据分镜挑最少的工具；候选先记清单，在独立测试项目验证后再采用。交付时更新导航、依赖记录和状态。清理前先说明具体目标和备份方式。
